Use case: SaaS

Membria Code learns from reverts

Solo developers · Claude Code, Codex, Cursor (API to B2B) · SaaSA hosted experience layer for developers who ship with Claude Code, Codex or Cursor. One MCP endpoint, a private graph per account, nothing to run.
1.
The situation
A developer asks Claude Code to add caching to an API client. The model reaches for an in-memory LRU — the same choice that broke under multi-worker deploys and was reverted two weeks ago. That lesson lives in an old transcript nobody will read.
2.
How it works
Before choosing, the model asks Membria for decision context. It gets back the reverted decision and its negative knowledge — per-process cache, inconsistent across workers, recorded with the decision — plus the commons signal: how often this pattern is removed in other projects.
3.
The result
The model picks a shared cache and records the decision with its alternatives. Two weeks later the change is still in place, and the outcome attaches itself from git — nobody writes a post-mortem. The model is unchanged and never grades its own work: the outcome comes from reality, and the next decision starts from what actually happened.

The situation
A team of six has to add rate limiting to the public API. Instead of six separate agent sessions, the task enters one pipeline: Researcher, Planner, Developer, Reviewer and Gate.

How it works

Case study · 03

AI-EPC from tender to issue

EPC contractors & design institutes · Worldwide · SaaS
1.
The situation
An EPC contractor uploads a tender folder: specifications, drawings, vendor catalogues, contract terms. This is where requirements get missed, and a late clause turns into rework — 28% of budget overruns.
2.
How it works
AI-EPC reads every file, scanned pages included, into a requirements register where each line cites its source clause. It builds the design level by level: models propose, rules, codes and catalogues accept or reject, and unknown values become questions to the customer.
3.
The result
Each discipline lead approves documents at a gate, and a change in one place reaches every dependent sheet. The contractor issues a consistent package with an evidence trail behind each document. Engineers sign; the system never stamps.

Case study · 04

Broker Platform one data bus

Licensed virtual-asset broker · Central Asia · client anonymised · On-Premise
1.
The situation
A licensed broker runs execution and compliance as two parallel tracks built by two vendors. An operation must not execute until compliance has decided on it, and personal data must stay out of shared systems.
2.
How it works
Membria owns the data bus and decision memory between the tracks: a Kafka backbone with 38 schema-validated event types and a graph of 42 object types. A client's status and every operation decision travel to the other track over the bus.
3.
The result
A compliance officer asks in plain language why an operation was blocked and gets the full chain — screening result, limit breaches, approval steps — with the source events. Both vendors integrate against one documented contract.

Case study · 05

Bank reporting & mortgage

Developer-owned bank · CIS · regulatory reporting, mortgage and escrow · On-Premise
1.
The situation
Methodologists spend 2–5 business days on each central-bank report specification. Mortgage review is a 40+ field manual checklist, and escrow specs are copied from the previous project.
2.
How it works
A reporting assistant writes the specification from a free-form task, using graphs of the bank's object model and the regulator's forms. Skills keep the mappings that worked; rejected mappings are never proposed again. A mortgage assistant checks each application against project and escrow data.
3.
The result
A specification is ready in 1–4 hours instead of 2–5 days, and when the regulator changes a form, every affected specification is listed at once. The bank picks its own model — Claude, GigaChat or on-prem Qwen — and data stays inside its security boundary.

Case study · 06

C2 Center: Palantir-class, ministry-owned

Ministry of Emergency Situations, Kazakhstan · National command system · In delivery
1.
The challenge
Emergency data sat in separate systems, and decisions depended on manual cross-checks. The ministry needed AI that would speed up command decisions without data leaving the country or decisions leaving human hands.
2.
What we built
A command platform where five AI agents assess risk, draft response plans, build routes, prepare alerts and analyse outcomes. Every recommendation comes with its sources and a confidence score. A quality gate blocks plans that repeat past mistakes, and the system learns from every incident.
3.
Why it stands out
It runs entirely inside the ministry’s network on its own AI models, and the ministry keeps the source code. Humans approve every action, in line with Kazakhstan’s new AI law.
